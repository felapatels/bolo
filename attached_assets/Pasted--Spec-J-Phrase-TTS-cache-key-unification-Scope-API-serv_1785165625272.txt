# Spec J: Phrase TTS cache key unification

Scope: API server only. Makes the phrase prewarm and the phrase playback route compute identical cache keys, and makes the prewarm synthesize with the configured provider instead of hardcoded ElevenLabs.

**Run this before Spec G, H, and I. It fixes a live defect that costs money on every startup and imposes a roughly twenty second wait on the first play of every phrase.**

## 2. Problem statement

**2.1 The prewarm and the playback route write to disjoint key namespaces.** The prewarm calls `ttsCacheKey(nativeScript, DEFAULT_VOICE, languageName, elevenLabsVoiceId)`, which SHA-256s five fields: text, voice, language name, ElevenLabs voice id, and `TTS_PROVIDER_VERSION`. The `/openai/tts` route, because `USE_ELEVENLABS_TTS` is false, calls `legacyTtsCacheKey(text, chosen, languageName)`, which SHA-256s three fields. A hash over five inputs can never equal a hash over three. The two sides operate in parallel namespaces with zero overlap.

The consequences are all live today:

- The prewarm spends ElevenLabs credits at every server startup writing entries nothing ever reads.
- Every phrase misses the cache on first play and synthesizes on demand. A measured request took 19,883ms.
- The route then writes its own entry under the legacy key, so phrases self-heal one at a time, each at the cost of one learner waiting roughly twenty seconds and one `gpt-audio` synthesis charge.

**2.2 The prewarm ignores the configured provider.** It calls `textToSpeechElevenLabs` unconditionally regardless of `TTS_PROVIDER`. The playback route synthesizes with `gpt-audio`. Even with matching keys, the two sides would produce audio from different providers in different voices.

**2.3 There is no cache hit or miss signal.** The route logs nothing about cache outcomes. The only way to infer a hit is by eyeballing response times, which is how this defect stayed invisible.

## 4. Behavior and logic

### 4.1 Single source of truth for phrase synthesis identity

1. Add a resolver in `ttsConfig.ts` that returns, for the currently configured provider, the three values that identify a synthesis: the provider name, the model name, and the voice used for phrase audio.
2. Both the prewarm and the playback route must obtain provider, model, and voice from this resolver. Neither may hardcode a voice, a model, or a provider name.
3. This resolver is the mechanism that prevents the defect from recurring. If the two sides can derive these values independently, they will eventually diverge again.
4. If the voice constants currently live in `parrotChat.ts` and importing them into `ttsConfig.ts` would create a circular import, **stop and ask**. Do not duplicate the constant values.

### 4.2 Unified key function

1. Add a new exported key function in `ttsCache.ts` for phrase audio.
2. It must incorporate: the phrase text, the provider, the model, the voice, and the language identifier, plus an explicit version segment for this key scheme.
3. Both the prewarm and the playback route must call this one function with arguments derived from the resolver in 4.1.
4. Do not modify `ttsCacheKey`, `legacyTtsCacheKey`, or `TTS_PROVIDER_VERSION`. Leave them in place. Other callers may still exist and this spec does not audit them.
5. Existing rows written under the old key schemes become orphaned. That is accepted and intentional. Do not delete them and do not write a migration.

### 4.3 Provider-aware prewarm

1. The phrase synthesis loop must synthesize using the provider indicated by the resolver, not unconditionally through ElevenLabs.
2. When the provider is ElevenLabs, preserve today's behavior including the quota monitor, circuit breaker, concurrency cap, and pacing delay.
3. When the provider is not ElevenLabs, synthesize through the corresponding provider path and do not consult the ElevenLabs quota monitor.
4. Preserve the existing skip-if-already-cached behavior, computing the lookup with the new key function.
5. Preserve the character budget mechanism and its environment variable. Do not change its default in this spec.
6. Leave the `warmGreetings()` gating exactly as it is. Greeting prewarm is a separate concern.

### 4.4 Playback route

1. Compute the lookup key with the new key function, using resolver-derived values.
2. On a miss, synthesize with the provider indicated by the resolver, then write the result under the same new key.
3. Preserve the existing response shape and status codes. This spec changes key derivation and provider selection only, not the contract.

### 4.5 Logging

1. Log one info-level line per phrase request with the prefix `[phrase-tts]` recording the provider, the model, the voice, the language, the character count, whether the lookup was a hit or a miss, and the elapsed milliseconds.
2. On the prewarm side, log a summary line at completion with the prefix `[phrase-tts]` recording the provider, how many phrases were already cached, how many were synthesized, how many failed, and whether the character budget was reached.
3. Do not log audio content or base64 payloads.

## 5. Acceptance checklist

1. The system shall provide a resolver returning the provider, model, and phrase voice for the currently configured provider.
2. The system shall derive provider, model, and voice in both the prewarm and the playback route exclusively from that resolver.
3. The system shall not hardcode a voice, model, or provider name in either the prewarm or the playback route.
4. The system shall provide a single phrase cache key function incorporating text, provider, model, voice, language identifier, and a key scheme version.
5. The system shall use that one key function in both the prewarm and the playback route.
6. The system shall produce identical keys on both sides for the same phrase under the same configuration.
7. The system shall leave `ttsCacheKey`, `legacyTtsCacheKey`, and `TTS_PROVIDER_VERSION` unmodified.
8. The system shall not delete orphaned cache rows and shall not include a database migration.
9. The system shall synthesize prewarm phrases using the configured provider rather than unconditionally through ElevenLabs.
10. The system shall preserve the ElevenLabs quota monitor, circuit breaker, concurrency cap, and pacing delay when the configured provider is ElevenLabs.
11. The system shall not consult the ElevenLabs quota monitor when the configured provider is not ElevenLabs.
12. The system shall preserve the skip-if-already-cached behavior using the new key function.
13. The system shall preserve the character budget mechanism and its environment variable, with its default unchanged.
14. The system shall leave the greeting prewarm gating unchanged.
15. The system shall synthesize on a playback cache miss using the configured provider and write the result under the new key.
16. The system shall preserve the existing response shape and status codes of the phrase playback route.
17. The system shall log an info-level `[phrase-tts]` line per phrase request recording provider, model, voice, language, character count, hit or miss, and elapsed milliseconds.
18. The system shall log a `[phrase-tts]` prewarm summary recording provider, already-cached count, synthesized count, failure count, and whether the budget was reached.
19. The system shall not log audio content or base64 payloads.
20. The system shall leave `parrotChat.ts`, the chat route, the greeting route, the greeting key helpers, and the cache schema unmodified.

## 6. Open questions

1. **Orphaned rows and a temporary regression.** Changing the key scheme means every phrase misses on first play after this ships, including phrases that had already self-healed. The prewarm will refill them, but until it does, first plays are slow again. This is a deliberate one-time cost in exchange for keys that cannot silently diverge. Confirm this is understood before implementing.
2. **The character budget will now matter.** With keys matching, the budget genuinely bounds how much of the library gets prewarmed. The default is small relative to a 22 language phrase library. Raising `TTS_PREWARM_CHAR_BUDGET` is a configuration change to make after this lands and after verifying keys match, not part of this spec.
3. **Interaction with Spec H.** Spec H adds a chat reply cache key. If Spec J lands first, Spec H should reuse the key builder introduced here rather than inventing a second scheme. Flag this if you see the two diverging.
4. Whether phrase voice should match chat voice is a product decision and is deliberately not settled here. This spec preserves whatever voice the phrase path uses today for the active provider.
