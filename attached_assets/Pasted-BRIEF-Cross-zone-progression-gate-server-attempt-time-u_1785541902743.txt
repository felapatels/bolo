BRIEF: Cross-zone progression gate (server) + attempt-time unlock hardening

CONTEXT
The journey is intended to be linear across zones, but deriveGroupStatuses (artifacts/api-server/src/lib/lessonGroupUnlock.ts:53-85) scopes to one (language, category) at a time and unconditionally unlocks each category's first group (line 66: previousClears = true). Within-zone sequential unlock works correctly via the shared guard in lessonGroupAccess.ts ("the ONE code path shared by the journey listing and every phrase-serving route"). The gap: nothing conditions a zone's first station on the previous zone, so a learner at Zone 1 Station 1 can practice Zone 6 Station 1 today via the Phrasebook, deep links, or any client. Ruling made: the journey is linear across zones. A zone's first station unlocks only when the previous zone is completed or tested out. Zone test-out is the designed escape valve and ships in the same build family; this gate must not ship to production ahead of zone test-out being available (flag or build sequencing per Step 0 findings).

STORY 1: Cross-zone gate in the shared unlock path
As a learner, I want zones to unlock in journey order, so that progression follows the line and skipping ahead is an explicit, designed action (test-out) rather than a side door.

Business value: Makes the map's linear boarding UX true at the serving layer, protects the zone test-out design (and its planned monetization) from a free bypass, and keeps one authoritative gate path.

Acceptance criteria:
1. The system shall unlock the first lesson group of a category only when the preceding category in the language's zone order is complete, where complete means every group in it has status completed or tested_out.
2. The system shall keep the first category of each language always eligible for its first group, preserving current behavior for Zone 1.
3. The system shall apply this gate in the shared unlock derivation consumed by the journey listing and every phrase-serving route, so the map and served content cannot disagree.
4. The system shall preserve the retake exemption unchanged: any phrase with a prior attempt by the user remains servable regardless of gating.
5. The system shall leave teaser/showroom serving behavior byte-identical for locked-language callers.
6. The system shall leave within-category sequential unlock behavior unchanged.

Implementation notes:
- The change belongs in or immediately around deriveGroupStatuses/the shared guard, not in individual routes; the diagnostic's "ONE code path" property must survive.
- Completion check should reuse the same stats source the within-zone derivation already loads where possible; avoid a second query pattern per category if the context loader can supply the predecessor's rollup cheaply. Report the query cost delta.
- Ungrouped phrases (lessonGroupId NULL) keep their current servability rule; this gate concerns grouped progression only.

STORY 2: Attempt-time hardening
As the system owner, I want progression enforced at write time as well as serve time, so that the gate holds even if phrase text reaches a client by any path.

Acceptance criteria:
1. The system shall reject attempt writes (POST /attempts) for phrases in groups the user has not unlocked, using the same shared guard, except where the retake exemption applies.
2. The system shall continue to accept attempts for ungrouped phrases and previously-attempted phrases unchanged.
3. The system shall return a distinct, non-retryable error for gated attempt writes, logged distinctly from entitlement denials.

Implementation notes:
- /openai/pronunciation stays out of scope: it scores audio, does not write progression; the ledger write is the enforcement point.
- Keep the check cheap: the unlock context is already loadable; do not add per-attempt heavy queries. Report the cost.
