## 1. Feature Summary

Restructure the prompts on the two highest-volume LLM routes so that OpenAI automatic prompt caching applies to the static portion of every request. Static instruction text (the pronunciation scoring rubric and the Bolo character persona) is currently rebuilt per request and may contain interpolated variables, which changes the prompt prefix on every call and prevents any cache hit. This change moves all static text into frozen module-level constants placed at the very front of the message array, and moves all variable content to the end.

No user-visible behavior changes. Model output quality must be unchanged. This is purely a cost optimization.

Target routes:
- `artifacts/api-server/src/routes/openai.ts` around line 780, the pronunciation LLM scoring call
- `artifacts/api-server/src/lib/parrotChat.ts` around line 421, the `reply()` chat text generation call

## 5. Behavior and Logic

### 5.1 Pronunciation scoring call (`openai.ts`)

1. Extract the full scoring rubric system prompt into a module-level constant named `PRONUNCIATION_RUBRIC_PROMPT`, declared once at the top of the file, outside any function.
2. The constant must be a plain static string literal. It must contain no template interpolation, no date, no timestamp, no language name, no user ID, and no request-specific value of any kind.
3. If any variable is currently interpolated into the system prompt (for example a language name or a difficulty level), remove it from the system prompt and add it to the user message instead, clearly labeled.
4. The message array must be constructed in this exact order: system message containing only `PRONUNCIATION_RUBRIC_PROMPT`, then the user message containing the target phrase, romanized form, english gloss, transcript, and any variables moved in step 3.
5. The user message must contain all request-specific content and nothing static.

### 5.2 Chat reply call (`parrotChat.ts`)

6. Extract the Bolo character system prompt into a module-level constant named `BOLO_PERSONA_PROMPT`, declared once at the top of the file, outside any function.
7. The same rules from steps 2 and 3 apply. The persona constant must be byte-identical on every request.
8. The message array must be constructed in this exact order: system message containing only `BOLO_PERSONA_PROMPT`, then prior history turns in chronological order oldest first, then the current user turn last.
9. IMPORTANT, this is the part most likely to be built wrong. The history window must not slide by one turn on each request. A rolling window that drops the oldest turn every turn changes the prompt prefix on every call and defeats caching entirely. Replace the current sliding window with block truncation: keep history until it exceeds 8 turns, then drop the oldest 4 turns at once and hold that boundary steady for the next 4 turns. The prefix must stay stable across consecutive turns within a conversation.
10. Do not reorder, summarize, or compress history content. Only change how truncation is triggered.

### 5.3 Instrumentation, required for both routes

11. After each of the two calls, read `usage.prompt_tokens_details.cached_tokens` from the OpenAI response and log it alongside `usage.prompt_tokens`.
12. The log line must use the format: `[cache] route=<pronunciation|chat> prompt_tokens=<n> cached_tokens=<n>`
13. Logging must not throw if `prompt_tokens_details` is absent from the response. Guard with optional access and default to 0.

### 5.4 Verification note for the agent

14. OpenAI prompt caching applies only to prompt prefixes above a minimum token length. The pronunciation rubric may fall below that threshold on its own. Do not pad, extend, or rewrite the rubric to reach it. Implement the reorder as specified, then report the observed `cached_tokens` values so the threshold question can be answered with real data rather than assumption.

## 6. Acceptance Checklist

1. The system shall produce identical pronunciation scores and feedback text for a given input compared to before the change.
2. The system shall produce chat replies of the same character and quality as before the change.
3. The system shall declare `PRONUNCIATION_RUBRIC_PROMPT` and `BOLO_PERSONA_PROMPT` as module-level constants containing no interpolated values.
4. The system shall place the static system message first in the message array on both routes.
5. The system shall place all request-specific content in the user message on both routes.
6. The system shall maintain a stable history prefix across consecutive chat turns and shall not drop exactly one history turn per request.
7. The system shall log `cached_tokens` and `prompt_tokens` after each call on both routes.
8. The system shall not throw when `prompt_tokens_details` is missing from the response.
9. The system shall leave all model strings, token limits, and request parameters unchanged.

## After The Build

Run a normal practice session and a chat session, then check the logs. On the chat route you should see `cached_tokens` climb to roughly the size of the persona prompt plus stable history from the second turn onward. If `cached_tokens` stays at 0 on both routes, the prefix is still changing per request and something static is still being interpolated. Send the log output back and it can be diagnosed from there.
