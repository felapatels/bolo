### Known current state (do not re-investigate)

- XP is never stored as a total. It is summed on read in `computeProgressMetrics` from `attempts.score`, `daily_quiz_completions.xp_awarded`, and `game_sessions.xp_awarded`.

- Spaced repetition exists as a Leitner ladder in `buildReviewSchedule` in `artifacts/api-server/src/lib/progressMetrics.ts`, intervals `[0, 1, 3, 7, 16]` days, promote at score ≥ 60, reset at < 60, graduate permanently at best-ever ≥ 80.

## 1. FEATURE SUMMARY

BOLO's scoring works, but three systems that should be separate are currently the same number. The pronunciation score doubles as XP, mastery is a permanent high-water mark derived from that same score, and the Leitner box is driven by it too. One measurement is doing four jobs.

This spec separates them into six subsystems, each with one job:

1. **Correctness** judges whether a response was right.
2. **Memory scheduling** decides when an item comes back.
3. **Ability and difficulty estimation** tracks how good the learner is and how hard each phrase is.
4. **XP** is an engagement currency and is never used to compute proficiency.
5. **Pronunciation banding** reports speech quality honestly, without false precision.
6. **Proficiency level** is derived from ability and never from XP.

Most of this is invisible to the user. It is foundational for every later spec, so it lands first.

### The two places this spec breaks the existing "derive everything from events" pattern

The current architecture recomputes every derived value from raw `attempts` rows at query time. That is a good pattern and this spec preserves it everywhere it can. It cannot be preserved in exactly two places, for these reasons:

- **FSRS state must be materialized.** FSRS stability and difficulty are path dependent and are updated by a library function per review. Replaying full history per phrase per query would be O(n) per item on every request, and unlike the Leitner ladder the update is not a cheap arithmetic step.
- **Elo item difficulty must be materialized.** Item difficulty is shared across all users, so it is not derivable from any single user's event history at all.

XP remains derived in spirit but moves to a ledger, because XP now depends on the learner's ability and the item's difficulty *at the moment of the attempt*, and those values change over time. A ledger row captures what was awarded and why; recomputation from raw events would produce different numbers later.

### 3.7 One-time backfill migration

Write a migration script that, for every existing user and phrase with at least one attempt:

1. Replays that phrase's `attempts` rows in chronological order through the FSRS library, mapping historical `score` to an FSRS rating using the same mapping defined in behavior rule 14, and writes the resulting state into `user_item_memory`.
2. Replays the same rows through the Elo update to seed `user_ability.theta` and the phrase's `elo_difficulty`.
3. Writes `xp_ledger` rows reproducing historical XP under the OLD rules, so that no existing user's visible XP total drops when the new rules take effect. Set `source` appropriately and `multiplier_reason` to `legacy backfill`.

Point 3 is not optional. Changing XP rules retroactively and shrinking someone's lifetime total is the fastest way to lose a user who has been with you since the beginning.

## 4. UI SPEC

Minimal. No new screens. Reuse existing components. Do not restyle anything.

### 4.1 Pronunciation result shows a band, not a number

This is a removal of something currently displayed. The 0 to 100 score must no longer appear anywhere in the user interface or in any API response consumed by the client.

Show exactly one of four states:

- `Nailed it`
- `Close`
- `Try again`
- `Didn't catch that`

Keep the existing `feedback` and `tip` text from the LLM rubric. Those are useful and stay. Only the number goes.

Rationale, for the record: the pipeline is Whisper plus an LLM rubric. Published research on automated pronunciation assessment reports correlation with human raters in the high 0.7s for good systems. A two-significant-figure score on top of that is precision the model does not have, and it tells heritage speakers they are 73% wrong when they are understandable.

If the app has an existing pill or badge component, reuse it. Do not build a gauge, meter, ring, or progress bar.

### 4.2 Answer feedback gains a typo state

For any text-entry exercise, support a third state between correct and incorrect. Use the existing correct treatment plus one line beneath showing the corrected form, in the pattern `Almost: नमस्ते`. Reuse the existing feedback text component.

### 4.3 End of lesson XP breakdown

Add one collapsible line to the existing summary, sourced from `multiplier_reason`:

```
+120 XP
  Base 80
  Difficulty bonus +25
  Review bonus +15
```

Collapsed by default. Reuse the existing summary row component.

### 4.4 Settings

Add a read-only row showing the detected timezone with a manual override select. Reuse the existing settings row component.

### 4.5 Empty and error states

- Review queue empty: `Nothing due right now. Everything's still fresh.`
- Transcription unavailable: `Didn't catch that`, with retry. Never surface a raw error and never record the attempt as incorrect.

## 5. BEHAVIOR AND LOGIC

Numbered, testable requirements. Implement all of them.

### Correctness engine

1. The system shall extend the existing `normalizeNative` function to treat anusvara and the equivalent conjunct nasal form as identical, so that `हिंदी` and `हिन्दी` match.
2. The system shall extend `normalizeNative` to strip zero width joiner and zero width non-joiner characters and to canonicalize nukta variants to a single form.
3. The system shall preserve the existing `normalizeLatin` folding behavior (`chh` to `ch`, `ee` to `i`, diacritic stripping, repeated letter collapsing) without modification.
4. The system shall build the candidate set for a phrase from its native script, its romanized form, and every entry in the new `accepted_answers` column.
5. For text-entry exercises, the system shall return `correct` on exact match of normalized strings against any candidate.
6. For text-entry exercises, the system shall return `typo` when the minimum Levenshtein distance to any candidate is within threshold, where the threshold is 0 for candidates of 3 characters or fewer, 1 for candidates of 4 to 8 characters, and 2 for candidates of 9 or more.
7. The system shall treat `typo` as correct for XP and scheduling purposes while displaying the corrected form.
8. The system shall accept Roman transliterated input for any phrase that has a romanized form, judged under the same rules.

### Memory scheduling: replacing Leitner with FSRS

9. The system shall replace `buildReviewSchedule` with an FSRS-backed scheduler using the `ts-fsrs` library. Do not write a custom scheduler.
10. The system shall use the library's default parameters with a desired retention of 0.90. Do not attempt per-user parameter optimization in this spec.
11. The system shall remove the permanent graduation rule entirely. No phrase is ever removed from the review population. High-performing phrases receive long intervals instead.
12. The system shall redefine mastery as `stability >= 21 days AND the most recent attempt was correct`. Mastery is therefore reversible: a lapse reduces stability and the phrase ceases to be mastered until it recovers.
13. The system shall update `masteredCount` in `GET /categories` to use the new definition, reading from `user_item_memory` rather than deriving from best-ever score.
14. The system shall map outcomes to FSRS ratings as follows: `incorrect` or pronunciation band `retry` maps to Again (1); `typo` or band `close` maps to Hard (2); `correct` or band `nailed` with latency above the user's rolling median maps to Good (3); `correct` or band `nailed` with latency at or below the user's rolling median maps to Easy (4).
15. The system shall compute the user's rolling median latency from their last 50 attempts, defaulting to 4000 ms when fewer than 10 attempts exist.
16. The system shall write updated FSRS state to `user_item_memory` after every scored attempt.
17. The system shall serve `/review/phrases` from `user_item_memory`, returning phrases where `due_at` is at or before now, ordered by `due_at` ascending, capped at 20.

### Ability and difficulty estimation

18. The system shall model ability and difficulty on the Rasch logit scale, where probability of a correct response is `1 / (1 + exp(-(theta - beta)))`.
19. The system shall initialize `theta` at 0.0 per user per language per skill, and `elo_difficulty` at 0.0 per phrase.
20. After every scored attempt, the system shall update both `theta` and the phrase's `elo_difficulty` using an Elo update with a dynamic K factor.
21. The system shall compute K as `0.4 / (1 + 0.05 * n)`, where `n` is `attempt_count` for the user update and `exposure_count` for the phrase update.
22. The system shall treat `correct`, `typo`, and band `nailed` as an observed score of 1.0; band `close` as 0.5; and `incorrect` or band `retry` as 0.0.
23. The system shall increment `attempt_count` and `exposure_count` on every scored attempt and record `theta_delta` and `beta_delta` on the attempt row.

### XP

24. The system shall stop using `attempts.score` as XP. This is the single most important change in this spec.
25. The system shall award pronunciation XP as `10 * band_factor * difficulty_multiplier * review_multiplier * decay_multiplier`, where `band_factor` is 1.0 for `nailed`, 0.6 for `close`, and 0.0 for `retry` or `nocatch`.
26. The system shall compute `difficulty_multiplier` as `clamp(1 + 0.5 * (elo_difficulty - theta), 0.25, 2.0)`.
27. The system shall apply a `review_multiplier` of 1.5 when the phrase was due per FSRS at the time of the attempt, and 1.0 otherwise.
28. The system shall apply a `decay_multiplier` of 0.1 when the phrase's stability exceeds 60 days and the phrase was not due. This is the primary anti-farming rule and must not be omitted or softened.
29. The system shall apply the same `difficulty_multiplier` and `decay_multiplier` logic to mini-game XP, using the mean difficulty of the phrases in that session, while keeping the existing flat base values (word-match 15, listen-and-pick 15, phrase-builder 20, speed-round 25, plus the existing 10 accuracy bonus).
30. The system shall leave daily quiz XP and Script Trace XP unchanged, since both are naturally capped and cannot be farmed.
31. The system shall write exactly one `xp_ledger` row per XP-awarding event, with a human readable `multiplier_reason`.
32. The system shall never use XP, in whole or in part, as an input to any proficiency, mastery, level, or ability calculation.
33. The system shall extend the existing signed `evaluationToken` to carry the computed XP amount alongside the score, so the client cannot submit its own XP.

### Streaks

34. The system shall unify streak logic on a single definition: consecutive calendar days in the user's IANA timezone with at least one qualifying activity. `computeDailyQuizStreak` and `computeQuizStreak` must stop using UTC `quiz_date` and use the same local-date logic as `computeStreakDays`.
35. The system shall preserve the existing behavior where a day with no activity yet falls back to yesterday, so a streak does not appear broken mid-day. This is correct and must not be changed.
36. The system shall capture the user's IANA timezone from the browser at signup and refresh it at the start of each session, writing to `users.timezone`.
37. The system shall stop silently defaulting to UTC when `users.timezone` is null. When null, use the timezone reported by the current request's client and persist it.
38. When a user's timezone changes and the change alone would break an otherwise intact streak, the system shall preserve the streak once and write the date to `users.tz_grace_used_on`, and shall not grant the grace again within 30 days.

### Pronunciation

39. The system shall keep the existing pipeline unchanged: Whisper transcription, the fast path at phonetic similarity ≥ 0.93 using `simToScore`, the LLM rubric path otherwise, and all of `applyScoreGuards` including the sibling-phrase wrong-phrase cap at 40.
40. The system shall map the resulting 0 to 100 score to a band as follows: 80 and above is `nailed`, 55 to 79 is `close`, below 55 is `retry`.
41. The system shall return only the band to the client. The numeric score shall not appear in any client-facing response payload.
42. The system shall return band `nocatch` and record outcome `discarded` when audio duration is under 400 ms or transcription fails. Discarded attempts award no XP, make no FSRS or Elo update, and count against the user in no way.
43. The system shall never deduct anything, break a streak, or apply any penalty as a result of a speaking attempt.
44. The system shall continue persisting `transcript`, `score`, and now `audio_duration_ms` on every attempt, so band thresholds can be recalibrated against real data later.

### Proficiency

45. The system shall derive any displayed BOLO Level from `user_ability.theta`, banded, and never from XP, lesson count, or attempt count.
46. The system shall not display a CEFR level anywhere. CEFR estimation requires a checkpoint assessment that is out of scope here.

### Anti-abuse

47. The system shall discard any text-entry attempt with latency under 250 ms, recording outcome `discarded` with a flag, awarding no XP and making no FSRS or Elo update.
48. The system shall calculate all XP, streak, theta, and beta values server side and ignore any such value received from the client.

## 6. ACCEPTANCE CHECKLIST

Verify each before declaring the build complete.

1. The system shall no longer award XP equal to the pronunciation score. A score of 73 shall produce a band of `close` and XP in the single digits after multipliers, verified by inspecting `xp_ledger`.
2. The system shall return a phrase to the review queue after a long interval rather than removing it permanently, verified by confirming a phrase with a historical best score of 95 has a non-null `due_at` in `user_item_memory`.
3. The system shall report zero or near-zero XP for repeated attempts on a phrase with stability over 60 days that is not due, verified across four consecutive attempts.
4. The system shall produce the same streak value from the general streak and the quiz streak for a user active on both, verified with a test user whose local date differs from UTC.
5. The system shall expose no numeric pronunciation score in any client-facing API response, verified by inspecting the raw payload of `POST /openai/pronunciation`.
6. The system shall accept `हिंदी` and `हिन्दी` as equivalent, and shall accept a romanized answer for a phrase that has a romanized form.
7. The system shall leave every existing user's visible lifetime XP total unchanged immediately after the backfill migration runs.
8. The system shall preserve the sibling-phrase wrong-phrase cap, verified by speaking a different phrase from the same language and confirming the band is `retry`.

Repeating the boundaries most likely to be crossed.

1. **Do not touch the Script Trace feature, the mascot, animations, sound, or any visual styling.** The only UI changes in this spec are the pronunciation band, the typo state, one collapsible XP line, and one settings row.

Three behavioral reminders, because they are the load-bearing changes:

- Rule 24: the pronunciation score stops being XP.
- Rule 11: permanent graduation is removed, so nothing ever leaves the review population.
- Rule 28: mastery decay is what prevents farming. Do not omit or soften it.
