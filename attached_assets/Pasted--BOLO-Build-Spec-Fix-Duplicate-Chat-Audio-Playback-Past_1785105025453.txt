## 1. Problem Statement

On a successful chat turn, two audio replies sometimes play simultaneously, overlapping each other. Reproduced on a turn that succeeded with no error and no retry, so duplicate network requests are not the cause. A single reply is producing two playbacks.

Two independent defects, either sufficient on its own:

**Defect A, double invocation.** The squawk sound effect wires the reply-playback function to three separate callbacks with no one-shot guard:

```
sfx.onended = playReply;
sfx.onerror = playReply;
sfx.play().catch(playReply);
```

If the browser rejects `play()` under autoplay policy and also fires `onerror`, `playReply` runs twice. Two `Audio` objects are created and both call `play()`.

**Defect B, orphaned playback.** `playReply` overwrites `playbackRef.current` without pausing what it currently points at:

```
const audio = new Audio(...);
playbackRef.current = audio;   // overwrites, does not pause
```

Any audio already playing is orphaned. Its reference is lost but it keeps playing to completion.

`startStreamPlayback` has the identical structure and the identical two defects.

## 5. Behavior and Logic

### 5.1 Shared stop helper

1. Add a helper function that stops and releases whatever is currently in `playbackRef.current`. It must: return immediately if the ref is null, otherwise call `pause()` on the element, clear its `onended`, `onerror`, and `onplay` handlers, set `currentTime` to 0, and set `playbackRef.current` to null.
2. Wrap the body in try/catch. A detached or already-disposed element must not throw.
3. Reuse this helper inside the existing `stopPlayback` rather than duplicating logic. Do not change `stopPlayback`'s external behavior or its call sites.

### 5.2 Pause before play

4. At the top of `playReply`, call the helper from step 1 before creating the new `Audio` object.
5. Do the same at the top of `startStreamPlayback`.
6. Only after the helper returns may a new `Audio` be constructed and assigned to `playbackRef.current`.

### 5.3 One-shot guard on the squawk callbacks

7. In every place where the reply-playback function is wired to `sfx.onended`, `sfx.onerror`, and `sfx.play().catch(...)`, introduce a local boolean flag scoped to that squawk sequence, initialized false.
8. Wrap the reply-playback function in a local wrapper that returns immediately if the flag is true, otherwise sets the flag to true and then invokes the real function.
9. Wire that wrapper to all three callbacks in place of the direct reference. All three remain wired. The guard, not the wiring, prevents the double call.
10. Apply this to both the `playReply` sequence and the `startStreamPlayback` sequence. Each sequence gets its own independent flag.

### 5.4 Mutual exclusion between playback paths

11. Determine whether `playReply` and `startStreamPlayback` can both be triggered for the same reply. Report the finding.
12. If they can, ensure only one runs per reply. Do not restructure the streaming logic to achieve this. A guard equivalent to steps 7 through 9, shared across both paths for a single reply, is sufficient.

### 5.5 Instrumentation

13. Log one line each time a reply playback actually begins, after the guard has passed: `[audio] play path=<reply|stream>`.
14. Log one line each time the guard blocks a duplicate invocation: `[audio] duplicate blocked path=<reply|stream>`.
15. These logs must contain no audio data, no base64, and no transcript text.

## 6. Acceptance Checklist

1. The system shall play exactly one audio reply at a time.
2. The system shall pause and release any currently playing audio before starting new audio.
3. The system shall invoke the reply playback function at most once per squawk sequence, regardless of how many of `onended`, `onerror`, and the `play()` rejection fire.
4. The system shall apply the same guarantees to the streaming playback path as to the non-streaming path.
5. The system shall not throw when the stop helper is called with a null or already-disposed audio element.
6. The system shall continue to play the squawk sound effect before the reply, unchanged.
7. The system shall continue to stop playback when the user taps to skip and when a new recording starts.
8. The system shall log `[audio] play path=<reply|stream>` when playback begins.
9. The system shall log `[audio] duplicate blocked path=<reply|stream>` when a duplicate invocation is prevented.
10. The system shall pass typecheck with no errors.

## After The Build

Run six or more chat turns and watch the console.

Expected: one `[audio] play` line per reply. Occasional `[audio] duplicate blocked` lines are fine and confirm the guard is doing its job.

The most reliable way to reproduce the original bug is a page load where autoplay is blocked, meaning you load the chat page and immediately record without clicking anywhere else first. That is the condition where `play()` rejects and the second callback fires.

If two voices still overlap after this, capture the console output. Two `[audio] play` lines for one reply means a third invocation path exists that was not found. Zero duplicate-blocked lines alongside overlapping audio means the overlap comes from somewhere other than these two functions.
