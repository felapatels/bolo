# BOLO Spec D1b-M: Journey Map Mobile Port (build 28 headline)

**Read docs/CODEBASE-FACTS.md before doing anything.** It is authoritative. Apply section 9 in full. If anything in this spec contradicts it, stop and ask.

Purpose: port the shipped web journey map to bolo-mobile so iOS carries the product's signature progression UX. The web implementation (journey.tsx, the serpentine track, ticket components, showroom/teaser states) is the reference implementation and the source of truth for behavior. This is a translation job, not a redesign: every behavior decision has already been made and shipped on web.

## SESSION RULES

1. No discovery beyond Step 0. No redesign, no "improvements" to the web behavior, no new states.
2. Server is DONE. The unlock model, latch, showroom access field, teaser, test-out, and unlock filtering are all live and shared. This spec touches bolo-mobile only. Zero api-server changes.
3. Visual parity target: same information, same states, same railway metaphor. Exact pixel parity is not required; native-feeling scroll and touch is.
4. All 22 lines with their existing names, zones, and station data come from the same endpoints web uses. No hardcoded content.

What is available and already in the bolo-mobile dependency tree for this: react-native-svg (present? version?), or would it need adding? ## BEHAVIOR (after Step 0 approval — all mirrors web)

1. Home gets the boarding-pass hero as the primary CTA (current-line name, next stop, progress at stop, "Continue your journey"), replacing none of the other home cards except positioning per web's layout.
2. The journey screen renders: line header (boarding pass), fare-zone postcards, serpentine (or approved simplified) track, stops with states — current (train marker + mascot), completed, locked, FREE TASTE, ALL-ACCESS — teaser chips, and the locked-stop dialog offering test-out where applicable.
3. Showroom mode for locked languages: same forced-locked rendering and access:"teaser" handling as web, never latching.
4. Stop taps route into practice with the group param. Locked stops open the dialog, never a dead tap.
5. Test-out entry from the dialog mirrors web.
6. States and copy come from the API; no client-derived unlock logic.

## ACCEPTANCE

1. The system shall render the journey screen for the active language with all stops in their server-reported states.
2. The system shall route stop taps to practice scoped to that stop's group.
3. The system shall render showroom mode for locked languages without writing any progress.
4. The system shall present test-out from locked-stop dialogs where the server offers it.
5. The system shall show the boarding-pass hero on home linking to the journey screen.
6. The system shall handle the 403 lesson_group_locked response with the locked dialog, not an error screen.

## OUT OF SCOPE

Server changes of any kind; web changes; the polish-batch items (nav restyle, Plus copy — separate task); B1 mobile parity (#861, separate task); Android.
