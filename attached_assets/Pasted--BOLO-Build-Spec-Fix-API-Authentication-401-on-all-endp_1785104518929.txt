## 1. Problem Statement

Every authenticated API endpoint returns 401 Unauthorized. Confirmed from a browser console capture covering 2,027 lines: `/api/entitlements`, `/api/account`, `/api/categories`, `/api/progress/summary`, `/api/attempts/recent`, `/api/review/phrases`, `/api/badges`, `/api/openai/chat-greeting`, and `/api/openai/chat` all return 401. No other error type appears in the capture.

Every one of those failures passes through the same stack frame: `custom-fetch.ts:382`.

Downstream symptoms, all caused by this single failure:
- Home page topic grid renders empty (`/api/categories` 401)
- Sidebar shows "Free plan" for a Plus account (`/api/entitlements` and `/api/account` 401)
- Chat fails with a client-side runtime error (`/api/openai/chat` 401)

Cookie inspection shows Clerk cookies (`__session`, `__clerk_db_jwt`, `__client_uat`) each present in **two copies with different values**, one partitioned and one not, all with `SameSite=None` and `Secure` set. The two copies hold different JWTs and drift apart, so whichever copy the browser sends may carry a stale token.

Additionally, a second symptom pattern reported by the user: the first chat turn of a session succeeds and the second fails with 401. Clerk session tokens are short-lived and require continuous refresh. A voice turn takes several seconds (record, upload, transcribe, generate, synthesize), so a token captured once at page mount can expire mid-session.

**Hypothesis to verify in Phase 1:** the client fetch wrapper relies on cookies for API authentication rather than requesting a fresh Clerk token per request.

## 4. Phase 2: Implementation

Build only after Phase 1 is confirmed.

### 4.1 Per-request bearer token

1. In the fetch wrapper, obtain a fresh Clerk session token immediately before each request using the Clerk SDK's token-getter method. Do not capture a token once at module load, at component mount, or in a closure.
2. Attach the token as `Authorization: Bearer <token>` on every outgoing API request.
3. Keep `credentials: "include"` if it is already set. Do not remove cookie-based auth in this change. The bearer token is added as the primary mechanism while the cookie path remains as fallback.
4. If the token-getter returns null or throws, do not send an `Authorization` header and do not throw. Let the request proceed and fail normally so the existing error path still works.
5. Do not cache the token in a module-level variable. The Clerk SDK handles its own caching and refresh internally.

### 4.2 Server acceptance

6. If Phase 1 finding 3 shows the server middleware does not accept bearer tokens, stop and report. Do not modify server auth without confirmation.
7. If it does accept bearer tokens, no server change is required.

### 4.3 Retry configuration

8. Configure the TanStack Query client so queries do not retry on 401 or 403 responses. Retrying an authentication failure cannot succeed and multiplies request volume.
9. Leave retry behavior for all other status codes unchanged.

### 4.4 Instrumentation

10. On any API response with status 401, log one line: `[auth] 401 path=<path> had_bearer=<true|false>`.
11. This log must not include the token value, any part of it, or any cookie value.

## 5. Acceptance Checklist

1. The system shall request a fresh Clerk session token immediately before each authenticated API request.
2. The system shall attach that token as an `Authorization: Bearer` header on every authenticated API request.
3. The system shall not store a session token in a module-level variable or a closure captured at mount.
4. The system shall proceed with the request without an `Authorization` header when the token-getter returns null, rather than throwing.
5. The system shall not retry queries that fail with 401 or 403.
6. The system shall log `[auth] 401 path=<path> had_bearer=<true|false>` on any 401 response.
7. The system shall never log a token value, a partial token, or a cookie value.
8. The system shall load the home page topic grid populated for a signed-in user.
9. The system shall display the correct plan tier in the sidebar for a Plus account.
10. The system shall complete at least four consecutive chat turns in one session without a 401.
11. The system shall pass typecheck with no errors.

## After The Build

Test in this order:

1. Open the app in a normal browser tab, not the Replit editor preview. Confirm topics load and the sidebar reads Plus.
2. Open the app inside the Replit editor preview. Confirm the same. This is the partitioned-cookie case and is the stricter test.
3. Run a chat session of at least four turns, deliberately pausing about a minute between turn one and turn two. This is the token-expiry case that produced the original report.
4. Check the console for any `[auth] 401` lines. If any appear with `had_bearer=true`, the token is being sent but rejected, which points at server-side verification rather than the client.
