# Spec E: Reply integrity and synthesis guard

Scope: API server only. Enforces the reply schema, removes the silent parse-failure fallback, and caps the text submitted for synthesis.

## 2. Problem statement

A learner turn rendered raw model output into the chat bubble and submitted that same raw output to speech synthesis. The output was a valid JSON object followed by several hundred repetitions of its closing characters. Three independent defects combined to produce this.

**2.1 The reply schema is not enforced.** The `reply` dependency calls the model with `response_format: { type: "json_object" }`. That mode guarantees syntactically valid JSON but validates against no schema. Field names, field presence, value types, and value length are requested in the prompt text only. Nothing at the API layer can reject a malformed or runaway response.

**2.2 Parse failure is silently swallowed.** `JSON.parse` is wrapped in a try/catch. On failure the catch assigns the complete raw model output to the `reply` field, sets the other two fields to empty strings, logs nothing, signals nothing to the caller, and continues down the normal success path. A parse error is therefore indistinguishable from a successful turn, and its payload is treated as legitimate reply text.

**2.3 Nothing bounds the text submitted for synthesis.** The string handed to `synthesize` is the parsed reply field with squawk tokens stripped and whitespace trimmed. There is no length check and no truncation. Because audio output is the dominant cost in this system, an abnormally long reply is also the most expensive possible failure.

Temperature is not set on the reply call, so it defaults to 1.0, which raises the likelihood of degenerate repetition.

## 4. Behavior and logic

### 4.1 Schema enforcement

1. Replace `response_format: { type: "json_object" }` with a strict JSON schema response format on the `reply` call.
2. The schema must declare exactly three properties, all required, with `additionalProperties` set to false, and all three typed as strings.
3. **Property order in the schema is behaviorally significant and must be preserved.** The reply field must be declared first, before the English gloss field. Generation follows schema order, and a prior defect was caused by the gloss being produced before the reply it was supposed to translate. Declaring them in the wrong order will reintroduce that defect.
4. Keep the property names exactly as they are today so that no downstream field access changes.
5. If the prompt text contains instructions describing the required JSON shape that are made redundant by the schema, they may be removed. If you remove or reword any part of the persona prompt, the persona cache key must be bumped by one version in the same change. If you change no prompt text, do not bump the key.
6. Set an explicit temperature on the reply call. Use 0.7. Do not leave it unset.
7. Leave `max_completion_tokens` at 300.

### 4.2 Parse failure handling

1. The catch block must no longer assign raw model output to the reply field. Under no circumstances may unparsed model output become reply text.
2. On parse failure, log one error-level line with the prefix `[reply]` recording that parsing failed, the length in characters of the raw output, and the finish reason from the completion if available. Do not log the raw output itself.
3. On parse failure, throw an Error rather than returning a value. The turn must fail cleanly so the existing client-side failed-bubble and retry affordance handles it. A learner seeing a retry control is correct behavior; a learner seeing raw model output is not.
4. Additionally validate the parsed object even when parsing succeeds: if the reply field is missing, is not a string, or is an empty string after trimming, treat it exactly as a parse failure per items 2 and 3.
5. Do not add a retry loop, a second model call, or any fallback generation. Fail the turn.

### 4.3 Synthesis length guard

1. Before the text is passed to `synthesize`, enforce a maximum length. Use 600 characters.
2. If the text exceeds the limit, do not synthesize and do not truncate silently into speech. Treat the turn as failed using the same path as Section 4.2 item 3.
3. Log one error-level line with the prefix `[reply]` when the guard trips, recording the actual character count and the limit. Do not log the text.
4. The guard applies to the same string that is passed to `synthesize`, after squawk stripping and trimming, so that it measures exactly what would have been billed.
5. The guard must sit before the synthesis call, not after, so that a runaway reply is never submitted for synthesis.

## 5. Acceptance checklist

1. The system shall request the reply completion using a strict JSON schema response format rather than generic JSON object mode.
2. The system shall declare exactly three required string properties in that schema with additional properties disallowed.
3. The system shall declare the reply property before the English gloss property in the schema.
4. The system shall keep the existing property names unchanged.
5. The system shall bump the persona cache key by one version if and only if persona prompt text was changed.
6. The system shall set the reply call temperature explicitly to 0.7.
7. The system shall leave the completion token ceiling at 300.
8. The system shall never assign unparsed model output to the reply field under any condition.
9. The system shall log an error-level line prefixed `[reply]` on parse failure recording the raw output length and the finish reason where available.
10. The system shall not log raw model output, reply text, or any generated content.
11. The system shall throw an Error on parse failure rather than returning a value.
12. The system shall treat a missing, non-string, or empty reply field as a parse failure.
13. The system shall not retry, re-call the model, or generate any fallback reply.
14. The system shall enforce a 600 character maximum on the text passed for synthesis.
15. The system shall fail the turn rather than synthesize or silently truncate when that limit is exceeded.
16. The system shall log an error-level line prefixed `[reply]` recording the actual character count and the limit when the guard trips.
17. The system shall apply the length guard to the post-squawk-stripping, post-trim string, and before the synthesis call.
18. The system shall leave `extractSquawks`, all TTS provider functions, the Spec D logging, history handling, and the SSE route unmodified.

---

## 6. Open questions

1. The 600 character limit is a first estimate based on observed reply lengths of roughly eight to nine seconds of speech. Once `[tts]` logging has accumulated real character counts across normal turns, this number should be revisited. If you find existing evidence in the codebase that normal replies routinely exceed 600 characters, stop and ask rather than shipping a guard that fires on healthy traffic.
2. If the installed OpenAI SDK version does not support strict JSON schema response formats, stop and ask. Do not fall back to `json_object` mode and do not upgrade the dependency.
