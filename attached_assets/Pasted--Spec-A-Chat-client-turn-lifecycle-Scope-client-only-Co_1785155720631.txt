# Spec A: Chat client turn lifecycle

Scope: client only. Covers abort handling, response validation, and pending bubble recovery.

## 2. Problem statement

Three defects in the chat turn lifecycle in the chat page component.

**2.1 No AbortController on chat fetches.** When a turn is interrupted, the fetch is never aborted. The connection stays open and the client keeps holding a reader on a stream it no longer consumes.

**2.2 No response.ok check before reading the SSE stream.** The code calls `getReader()` on the response body behind a non-null assertion without first checking status. On a non-200 response this throws a non-Error value, which surfaces to the learner as "unknown runtime error" with no diagnostic content.

**2.3 Pending learner bubble is never cleared in the outer catch blocks.** A pending learner bubble is pushed at the start of every turn. Two error paths already clear it correctly: the audio duration gate and the server noSpeech response. The outer catch blocks do not. On a network failure, a non-200 response, or an uncaught exception inside the SSE loop, the bubble is left in state with empty text and gets flattened into later prompts as an empty "Learner:" line.

**Critical structural note.** The send function contains two parallel and independently written SSE code paths inside the same function body: a greeting path used on the first turn when a pre-fetched greeting exists, and a normal path used for every other turn. Each has its own fetch, its own reader, and its own catch block. Every change in this spec applies to both paths. A change applied to only one path will appear to work in normal conversation and fail on first turns.

## 4. Behavior and logic

### 4.1 AbortController

1. Add a ref that holds the AbortController for the in-flight turn.
2. At the start of the send function, before either fetch is issued, abort any controller still held in that ref from a previous turn, then create a fresh controller and store it in the ref.
3. Pass the controller signal to both the greeting path fetch and the normal path fetch.
4. On component unmount, abort whatever controller is held in the ref.
5. Abort must reuse the existing turn-abandonment teardown rather than introduce a second mechanism. The component already abandons turns by comparing the active turn ref against the local turn id and then calling stream teardown and reader cancel. Abort handling routes into that same teardown.
6. An AbortError must not set the phase to "error" and must not display an error message to the learner. An abort is intentional and silent.
7. When a turn completes normally, clear the controller ref.
8. Under the current server configuration no audio element exists for a turn until the final reply event arrives, so an abort before that point has no audio to stop. Call the existing teardown functions anyway so behavior stays correct if streaming synthesis is later enabled.

### 4.2 Response validation

1. Immediately after each fetch resolves, and before any access to the response body, check the ok property of the response.
2. If the response is not ok, read the body as text inside a guard that tolerates an empty or unreadable body, then throw a real Error instance whose message contains the HTTP status code and the first 200 characters of that body text.
3. If the response is ok but the body is null, throw a real Error instance stating that the response contained no body.
4. Remove the non-null assertions on the response body in both paths. The null case is now handled explicitly by item 3.
5. No code path introduced by this spec may throw a value that is not an Error instance.

### 4.3 Pending bubble recovery and retry

1. Extend the ChatMessage type with an optional boolean `failed` field, alongside the existing optional `pending` field.
2. In both outer catch blocks, the pending learner bubble must always be resolved. It may never be left in the pending state.
3. If the transcript SSE event arrived before the failure, convert the pending bubble into a failed bubble: set pending to false, set failed to true, and set the bubble text to the received transcript.
4. If no transcript arrived before the failure, remove the pending bubble, matching the behavior the duration gate and noSpeech paths already implement.
5. Apply the same two rules on abort. A transcript received before the abort produces a failed bubble. No transcript produces a removal.
6. Store the recorded audio blob for the current turn in a ref so a failed turn can be retried. Retry re-sends the stored blob through the normal turn path. Retry does not require the learner to record again.
7. A bubble with failed set to true renders with a retry control. Activating it clears the failed flag, restores the bubble to pending, and re-runs the turn using the stored audio blob.
8. Messages with pending true or failed true must be excluded from the history array sent to the server, so that an empty or failed learner line can never enter a prompt.
9. Clear the stored audio blob ref when a turn completes successfully.

## 5. Acceptance checklist

1. The system shall create a new AbortController at the start of each turn and abort any controller remaining from a previous turn before doing so.
2. The system shall pass the abort signal to both the greeting path fetch and the normal path fetch.
3. The system shall abort the in-flight controller when the chat component unmounts.
4. The system shall route abort handling through the existing turn-abandonment teardown rather than introducing a second teardown mechanism.
5. The system shall not set the error phase and shall not display an error message to the learner when a turn ends due to an abort.
6. The system shall clear the controller reference when a turn completes normally.
7. The system shall check the response ok property before accessing the response body in both the greeting path and the normal path.
8. The system shall throw an Error instance containing the HTTP status code and up to the first 200 characters of the response body when a chat response is not ok.
9. The system shall throw an Error instance when a response is ok but its body is null.
10. The system shall contain no non-null assertion on the response body in either path.
11. The system shall never throw a non-Error value from any code path introduced by this spec.
12. The system shall resolve the pending learner bubble in both outer catch blocks, leaving no bubble in the pending state after a failure.
13. The system shall convert the pending bubble to a failed bubble carrying the transcript text when a transcript was received before the failure.
14. The system shall remove the pending bubble when no transcript was received before the failure.
15. The system shall apply the same bubble resolution rules on abort as on error.
16. The system shall retain the recorded audio blob for the current turn so that a failed turn can be retried without re-recording.
17. The system shall render a retry control on any learner bubble marked failed.
18. The system shall re-run the turn using the stored audio blob when retry is activated, and shall return the bubble to the pending state while it runs.
19. The system shall exclude all messages marked pending or failed from the history array sent to the server.
20. The system shall clear the stored audio blob when a turn completes successfully.
21. The system shall apply every change in this spec to both the greeting path and the normal path.

## 6. Open questions

1. Retry re-sends the stored audio blob, which means Whisper transcription runs a second time for that turn. This is intentional and keeps retry entirely client-side. If you would prefer retry to skip transcription by submitting the existing transcript as text, that requires the chat endpoint to accept a text turn, which pushes the change into server scope and out of this spec. Confirm before implementing an alternative.
2. If the recorded audio blob is not available at the point where the catch block runs, stop and ask rather than falling back to a retry control that cannot function.
