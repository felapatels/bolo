# Spec K: Reliable short-recording detection

Scope: Chat client only. Replaces an unreliable duration probe with a measurement that always produces a value, and adds a size floor so empty recordings never reach the server.

---

## 2. Problem statement

**2.1 The duration gate rarely runs.** `finishRecording` measures recording length by creating an `<audio>` element via `URL.createObjectURL(blob)` and reading `probe.duration` on `loadedmetadata`, with a 500ms timeout. MediaRecorder produces WebM as a live container with no Duration element in its header, so browsers commonly report `Infinity` for it. The gate is guarded by `Number.isFinite`, so a non-finite result skips the check entirely and lets the recording through. The 0.4 second threshold therefore does not protect the cases it was written for.

**2.2 Empty recordings reach the transcription API.** A hold too brief to produce a complete WebM Cluster still carries a valid EBML header. Server-side magic-byte detection labels it `webm` and forwards it unchanged. The transcription API rejects it with a 400 reading that the audio file may be corrupted or unsupported, and the learner sees a generic failure with no useful guidance.

**2.3 The measurement the server wants is already available and not being taken.** `runParrotTurn` accepts `clientDurationSeconds` and takes a slower path involving a WAV conversion purely to derive duration when it is absent. The recorder knows exactly when it started and stopped and could supply this directly.

## 4. Behavior and logic

### 4.1 Wall-clock duration measurement

1. Record a timestamp when recording actually starts and another when it stops, inside `useVoiceRecorder`.
2. Expose the elapsed duration in seconds as part of what `stopRecording` resolves with, alongside the existing blob.
3. This value must always be a finite number. It must never be `NaN`, `Infinity`, or undefined.
4. Do not remove the existing blob from what `stopRecording` returns. Existing callers depend on it.

### 4.2 Gate on the reliable measurement

1. Use the wall-clock duration from 4.1 as the gate input. Remove the `<audio>` element probe, the object URL, and the 500ms timeout entirely.
2. Because the measurement is now always finite, remove the skip-when-not-finite behavior. The gate must always evaluate.
3. Lower the threshold to 0.25 seconds. Wall-clock time includes button press and release overhead that decoded audio length does not, and a single short word can be under 400ms of speech.
4. Preserve the `if (!isRetry)` guard, the pending bubble removal, the phase return to idle, and the learner-facing message exactly as they are.
5. Preserve the `[stt] skipped reason=too_short` console log and extend it with the measured duration so the threshold can be tuned from real data.

### 4.3 Size floor

1. Reject a recording whose blob byte length falls below a minimum, independent of duration. A container with headers but no audio frames is small in a way duration alone may not reveal.
2. Use 2048 bytes. Log `[stt] skipped reason=too_small` with the actual byte length.
3. On rejection, take the identical path as the duration gate: remove the pending bubble, show the same learner-facing message, return to idle, and make no API call.
4. Apply this check after the duration gate.

### 4.4 Send the measurement to the server

1. Include the wall-clock duration in the request body as `clientDurationSeconds`, in seconds, alongside `audioBase64` and `audioMimeType`.
2. Send it on both the greeting path and the normal path in `finishRecording`.
3. Do not change any other field in the request body.
4. Do not modify how the server uses this value. That is out of scope.

## 5. Acceptance checklist

1. The system shall record start and stop timestamps in the recorder and expose the elapsed duration in seconds from `stopRecording`.
2. The system shall always produce a finite duration value, never `NaN`, `Infinity`, or undefined.
3. The system shall continue to return the recorded blob from `stopRecording`.
4. The system shall gate on the wall-clock duration and shall no longer create an `<audio>` element, an object URL, or a probe timeout for this purpose.
5. The system shall always evaluate the duration gate rather than skipping it on a non-finite value.
6. The system shall use a duration threshold of 0.25 seconds.
7. The system shall preserve the retry guard, the pending bubble removal, the return to idle, and the existing learner-facing message.
8. The system shall log `[stt] skipped reason=too_short` including the measured duration.
9. The system shall reject recordings whose blob is smaller than 2048 bytes.
10. The system shall log `[stt] skipped reason=too_small` including the actual byte length.
11. The system shall handle a size rejection identically to a duration rejection, making no API call.
12. The system shall evaluate the size floor after the duration gate.
13. The system shall include `clientDurationSeconds` in the request body on both the greeting path and the normal path.
14. The system shall change no other request body field.
15. The system shall leave `validateTranscript`, the transcription hint, the audio format helpers, the MIME preference order, and the recorder timeslice unmodified.

## 6. Open questions

1. The 0.25 second and 2048 byte values are estimates. The extended log lines exist so they can be tuned against real recordings. If you find existing evidence in the codebase that legitimate recordings fall below either value, stop and ask.
2. If `stopRecording`'s return shape is consumed anywhere outside the two files in Section 3, stop and ask rather than changing its signature.
