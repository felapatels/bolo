# BOLO Feature Build Spec: Contact Us Form (Settings Page)

Build exactly what is specified below. Do not plan, propose alternatives, or restructure existing code. If something is ambiguous, choose the simplest implementation consistent with the existing codebase patterns.

## 1. Feature Summary

Add a "Contact Us" entry point on the Settings page. Tapping it opens a contact form. When the user submits the form, the app emails the submission to LARKsupport@gmail.com and stores a copy in the database as a backup. This gives users a support channel and gives the owner a reliable record of every message.

## 2. Scope Boundaries

- Only touch: the Settings page (add one button/row), one new Contact form view, one new backend endpoint, one new database table, and email-sending setup.
- Do NOT redesign, restyle, or refactor the Settings page or any other screen.
- Do NOT add a support inbox, admin view, ticket system, or reply functionality.
- Do NOT modify authentication, user profiles, or any existing lesson/learning features.

## 3. Data Model Changes

Create one new table: `contact_submissions`

- `id` (primary key)
- `user_id` (nullable foreign key to users, populated when the submitter is logged in)
- `name` (text, required)
- `email` (text, required)
- `category` (text, one of: "Bug", "Feature Request", "Content Correction", "Other")
- `message` (text, required, max 2000 characters)
- `email_sent` (boolean, default false; set true after the notification email succeeds)
- `created_at` (timestamp, default now)

No changes to any existing tables.

## 4. UI Spec

**Settings page:**
- Add one new row/button labeled "Contact Us" with a mail icon, placed after the existing settings options and before any logout/danger-zone items.
- Match the exact visual style of the existing settings rows. Reuse the existing row/list component; do not create a new component style.

**Contact form (new view, opened from that button):**
- Title: "Contact Us"
- Fields in order:
  1. Name (text input, required; prefill from the user's profile if available)
  2. Email (email input, required; prefill from the user's account email if available)
  3. Category (dropdown/select, required; options: Bug, Feature Request, Content Correction, Other; default: Other)
  4. Message (multiline textarea, required, max 2000 characters, with a live character counter)
- Submit button labeled "Send Message", disabled while any required field is empty or while a submission is in flight.
- States:
  - Loading: button shows a spinner and is disabled during submission.
  - Success: replace the form with a confirmation message: "Thanks! Your message has been sent. We'll get back to you soon." plus a button to return to Settings.
  - Error: keep the form contents intact and show an inline error: "Something went wrong sending your message. Please try again."
- Match the app's existing form styling, colors, and typography. Reuse existing input components.

## 5. Behavior / Logic

1. When the user taps "Contact Us" on the Settings page, the system shall open the contact form view.
2. When the form is submitted, the client shall validate that name, email, category, and message are present, the email is a valid format, and the message is 2000 characters or fewer, before calling the backend.
3. The backend shall expose a POST endpoint (e.g., `/api/contact`) that re-validates all fields server-side and rejects invalid payloads with a 400 response.
4. On a valid submission, the backend shall first insert the record into `contact_submissions`, then send a notification email to LARKsupport@gmail.com.
5. The notification email subject shall be: "BOLO Contact Form: [Category] from [Name]". The body shall include name, email, category, message, user_id (or "not logged in"), and submission timestamp.
6. If the email sends successfully, the system shall set `email_sent = true` on the record. If email sending fails, the record shall remain in the database with `email_sent = false`, and the endpoint shall still return success to the user (the database copy is the fallback; do not lose the message or show the user an error for an email-provider failure).
7. The endpoint shall return an error to the client only if the database insert itself fails.
8. The backend shall rate-limit submissions to a maximum of 3 per user (or per IP for anonymous users) per 10 minutes, returning a 429 with a friendly message that surfaces in the form's error state.
9. Email sending: use the Resend account already linked to this app. Reuse the existing Resend configuration, API key secret, and verified sender exactly as currently set up; do not create a new integration, add a new secret, or change the sender domain.

## 6. Acceptance Checklist

- [ ] "Contact Us" row appears on the Settings page, styled identically to existing rows.
- [ ] Form opens with name/email prefilled for a logged-in user.
- [ ] Submitting with any empty required field is blocked client-side with a clear indication of the missing field.
- [ ] A valid submission creates a row in `contact_submissions` with all fields populated.
- [ ] A notification email arrives at LARKsupport@gmail.com with the specified subject and body format.
- [ ] If email sending fails, the submission is still saved and the user still sees the success state.
- [ ] The 4th submission within 10 minutes is rejected with the rate-limit message.
- [ ] Success and error states render as specified; form contents are preserved on error.

## 7. Out of Scope (Reminder)

- No admin dashboard or inbox for reading submissions.
- No changes to any screen other than Settings plus the new form view.
- No refactoring of existing components, routes, or styles.
