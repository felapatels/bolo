Voice data contribution program design spec ("Contribute your voice"). REPORT ONLY — no production code changes, no schema migrations, no consent UI built, no store attestations changed; deliverable is docs/specs/voice-data-program.md plus findings. Consult docs/CODEBASE-FACTS.md, agent memory, docs/specs/pronunciation-scoring-v2.md (this program rides build 32 with it), docs/specs/token-economy.md (Chai incentive integration), and the Android parity spec's data-safety section. Implementation targets build 32 alongside scoring v2; every item gated on build 31 beta approval.

Non-negotiable principles to design within: opt-in only, default OFF, no dark patterns; retention only of attempts made while the flag is on; full deletion on request and on account deletion; purpose-bound (scoring calibration and evaluation of pronunciation models); voice treated as sensitive data throughout.

Spec sections:

Consent UX. The opt-in surface: where it lives (account settings as the permanent home; plus one non-blocking introduction moment — propose where, and explicitly NOT a first-run interstitial or anything resembling a consent wall), exact plain-language copy explaining what is kept (your practice recordings plus their scores), what for, for how long, and how to delete; the toggle's off/on/off semantics (turning off stops future retention; state clearly whether it also deletes past contributions or leaves them until deletion is requested — recommend and justify one); Chai incentive design per the token-economy spec (a small one-time Chai grant for enabling, NO recurring payment per clip, and the copy must not make it feel like selling your voice — propose amounts and copy); minors consideration: account terms are 13+, state whether the program should exclude under-18 accounts where age is known and recommend.
Legal and policy surface. Privacy policy additions (draft the actual section text); iOS privacy label changes (which categories flip and to what); Google Play data safety form changes against the Android spec's draft table (audio becomes collected-and-retained-with-consent; produce the corrected rows); DPDP (India), GDPR/UK, and US state law posture at the level appropriate for a solo developer: consent basis, deletion rights, breach duty — flag anything that genuinely needs a lawyer's eyes rather than pretending to settle it; OpenAI processing disclosure unchanged vs changed, state which.
Storage and data architecture. Where clips live (object storage; evaluate what the current stack offers — check what storage the Replit deployment and existing infra can reach, or specify an external bucket with credentials as a deployment secret), path/key scheme keyed by user id + attempt id, encryption at rest expectations, retention window (propose a defined maximum, e.g. 24 months, rather than indefinite — justify), and the linkage design: clip reference stored on/beside the attempts row joining audio to transcript, band, ensemble grades, language, and scoring_path — the labeled-dataset join spelled out. Size and cost the storage at realistic volumes (e.g. 5%/15%/30% opt-in at 10K and 100K monthly attempts, ~50KB per 3s clip at the current preset).
Deletion machinery. Per-user deletion (settings action and support path): what gets removed, from where, in what timeframe; account-deletion integration with the existing deletion flow (read the current account deletion implementation and quote where the hook goes); the audit answer for "prove it's gone."
Server enforcement. Retention decision made server-side at attempt time from the user's flag (never client-asserted), the write path relative to the scoring v2 pipeline (clip is already in memory server-side during eval — retention is a tee, not a new upload), failure posture (retention failure never affects the attempt result), and the flag's storage (users table or preferences — follow the existing preference pattern, cite it).
Access and use governance. Who/what reads the corpus: the pilot/calibration harness and offline evaluation only; no third-party sharing beyond processors already disclosed; a one-paragraph internal policy statement suitable for the privacy page's "how we use it" claim.
Build-32 task breakdown. Ordered, sized, file-owned tasks slotted against the scoring v2 breakdown (consent UI + flag, storage write path, deletion integration, policy/label updates, store re-attestations), with the explicit rule that retention ships OFF-by-default and can ship dark (flag exists, program not promoted) if 32's schedule tightens.

Findings section: current account-deletion implementation reality, storage options actually available to this deployment, and every question requiring Aakesh's or a lawyer's decision, listed bluntly. No em dashes anywhere.
