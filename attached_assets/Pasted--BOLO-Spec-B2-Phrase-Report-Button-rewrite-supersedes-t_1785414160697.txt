# BOLO Spec B2: Phrase Report Button (rewrite, supersedes the July 28 version)

**Read docs/CODEBASE-FACTS.md before doing anything.** It is authoritative. Apply section 9 in full. If anything in this spec contradicts it, stop and ask.

Purpose: any learner can flag a phrase as incorrect in two taps, with an optional note. Reports land in a table for later review. This converts a trust-destroying moment (a native speaker spotting a wrong transliteration) into a contribution. It is the cheapest quality mechanism the app will ever have.

## SESSION RULES

1. No discovery or planning beyond Step 0.
2. No refactoring or improving anything not named here.
3. Keep it small. No moderation dashboard, no admin UI, no statuses, no email notifications, no report categories beyond the fields below.

## BEHAVIOR

1. A small, low-prominence flag affordance on the phrase card during practice (web and mobile). Two taps total: tap flag, tap a reason. Reasons: "Translation wrong", "Transliteration wrong", "Audio wrong", "Other". Optional free-text note (single field, 280 chars max), never required.
2. Submission is fire-and-forget: optimistic "Thanks, we'll check it" toast, no blocking spinner, failures silent to the user.
3. Server: POST /phrases/:id/report, authenticated. Stores user_id, phrase_id, reason, note, language_code, created_at in a phrase_reports table. Additive migration only.
4. Rate limit: max 20 reports per user per rolling hour, server-side, using the same DB-backed pattern as the test-out throttle. Over-limit submissions return a silent 200 and are not stored.
5. Duplicate reports (same user, same phrase) are allowed and stored; dedup is a review-time concern, not a write-time one.
6. No client behavior changes based on report state. The phrase renders identically after reporting.

## ACCEPTANCE

1. The system shall store a report row with reason and optional note on submission.
2. The system shall return 200 and store nothing beyond the cap of 20 per user per rolling hour.
3. The system shall not block, delay, or visually alter practice flow on submission success or failure.
4. The system shall require authentication on the report endpoint.

## OUT OF SCOPE

Admin/review UI, notifications, report resolution workflow, content edits, unreported-phrase analytics, bolo-mobile store build (mobile UI code may be written but ships with build 27, not a dedicated build).
