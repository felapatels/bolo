---
name: dev-DB drizzle migrate silently no-ops (poisoned created_at)
description: Why drizzle-kit migrate "succeeds" on the shared dev DB but never applies new migrations, and how to detect/handle it.
---

**Proven mechanism (Aug 4, 2026, Referral R1 incident):** the shared dev DB's `drizzle.__drizzle_migrations` was hand-healed in the past and one row carries a non-epoch `created_at` of `20260802230000` (a date literal, ~2.026e13, numerically larger than any epoch-millis value). Drizzle's migrator applies journal entries with `when > max(created_at)`, so EVERY new migration is treated as already applied on dev: `drizzle-kit migrate` reports success, runs no DDL, and inserts NO hash row. (Earlier note said "records hash without DDL" — that was wrong; nothing is written at all.) The dev hash table also has fewer rows (31) than journal entries (41) from prior out-of-band history. Fresh databases are unaffected: the full-chain check (`check-migrations.sh`, throwaway DB) applies everything cleanly, and publish computes its own schema delta for prod, so the anomaly is dev-local.

**Rule:** after `drizzle-kit migrate` on the dev DB, verify the new object exists with `to_regclass()` before trusting the success message. Detection shortcut: `select max(created_at) from drizzle.__drizzle_migrations;` — if it exceeds current epoch millis, dev migrate is dead.

**Fix pattern (local unblock):** apply the committed migration SQL by hand — `psql "$DATABASE_URL" -1 -f <(sed 's/--> statement-breakpoint//g' drizzle/<file>.sql)` — never hand-edit the migration file, then validate via the db-migrations (fresh-chain) and db-drift workflows. Note this leaves no hash row on dev for that migration.

**Deeper root cause (proven by scratch-DB probe, Aug 4, 2026):** the poison is in the COMMITTED JOURNAL, not just the dev row: `_journal.json` entry `0038_token_fk_cascade` itself has `when: 20260802230000` (date literal). drizzle-kit migrate applies entries with `when > max(created_at)` read once up front, so ANY database that runs the chain ends with max=20260802230000 and dead incremental migrates (fresh DBs pass the full-chain check only because the comparison baseline is read before the loop). DB-side normalization alone CANNOT heal it: the probe showed that after updating the 0038 row to epoch millis, the next migrate re-applies 0038 (its drop-then-add DDL happens to be re-runnable, so no error) and re-inserts created_at=20260802230000, silently restoring the poison. The only real heal is a repo-side journal fix (0038 when -> its true epoch value, 2026-08-02T23:00Z = 1785711600000) PLUS matching row updates/inserts on every long-lived DB; do both together or not at all.

**HEALED (Aug 4, 2026, owner-approved):** journal 0038 when fixed to 1785711600000 and dev DB normalized (row updated + 10 missing hash rows inserted, 31 -> 41 rows, max = 1785857394692). Dev incremental migrate is ALIVE again: two consecutive migrate runs clean, count stable at 41; fresh-chain scratch DB also 41/stable. The hand-apply psql pattern above is now only for genuinely out-of-band situations, not the default. Prod carries NO drizzle schema at all (verified via read replica: only _system/information_schema/public exist) because publish applies its own schema diff; prod never reads created_at and never needs this normalization.
