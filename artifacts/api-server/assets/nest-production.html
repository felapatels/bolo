04 / What to say, and what it is made of

Pitch

The words for a person, and the stack for an engineer. Both are true as of this snapshot.

A child in Ohio, speaking Gujarati back to a parrot.

One line

Bolo teaches children the languages of India by ear, the way a grandparent would: say it, hear it back, try again.

Thirty seconds

Millions of South Asian families are one generation away from losing the language at home. The apps that exist teach European languages to adults by making them tap at flashcards. Bolo starts with the mouth instead: it speaks a phrase, the child says it back, and it scores the attempt and answers in the voice of a cheeky parrot rather than a test. It covers all twenty two of India's scheduled languages, and it teaches the alphabet by hand, from strokes traced by real family members rather than a font. It is live on the App Store today.

If they ask why it is different

We learn the learner's pace and move with it. Ability is modelled per learner, so the next lesson meets them where they are instead of marching everyone through the same list.

Writing is inside the lessons, not a separate app and not a separate purchase. A child learns to say it and to write it in the same sitting.

And it stays fun. A parrot who talks back, chai to earn and spend, streaks and games. A child comes back without being told to, which is the only retention that matters at this age.

Proof, not promises

  • Live on the App Store since 21 Aug 2026, version 1.0.2.
  • 22 languages with journey 1 content. Journey 2 generated across all 22 on 24 Aug, not yet QA reviewed.
  • Devanagari 48 letters and Gujarati 45 traced by hand by a real contributor, scoring 75 on average against the grader.
  • Around 3,400 automated tests across the three suites: api 1,174, web 1,184, mobile 1,180.
  • Five languages withdrawn on quality rather than shipped. Reviews are in the Library.

How it makes money

  • Free tier, the default for every new account.
  • Plus, all access, monthly or annual. RevenueCat on mobile, Stripe on web, and the server is authoritative.
  • Family, four seats. Sale is switched off on web as of 24 Aug because neither store sells the equivalent, so a phone would not honour it. Existing families keep working.
  • Chai packs, one time, three sizes, credited only by the webhook.
  • One Language is dead: no package, no purchasers, though the gating still branches on it.

Prices are deliberately not written down anywhere in the codebase. They are read from Stripe through /api/pricing so a displayed price can never drift from the real charge.

05 / What bites

Traps

Facts that cost days when forgotten. Each one was paid for.

Ops

This cockpit is moving into the customer-facing app, and that was a decision.bolo-india.app is what learners open. Once the Nest lives there, every product deploy can break the cockpit and the cockpit's bugs ship inside the product bundle. The owner was told that plainly on 24 August and chose it anyway, which is the right way round. It is written here so the next person knows it was weighed rather than missed.

Ops

A Cloudflare redirect cannot serve bolo-india.app.The domain is DNS only, grey cloud: it answers "Google Frontend" through Replit with no cf-ray header, so Cloudflare Rules never see the traffic. Any redirect has to be a route in the app and a deploy. Checked 24 August after assuming otherwise.

Ops

A publish that dies at Build with no error is the image being too big.Provision and Security checks pass, Build goes red, Bundle and Promote never start, and Replit says "usually caused by a build command error". It is not. Read the build log's LAST line: if all five package builds finished and postBuild printed "Removed all cached metadata files" and then it simply stops, that is a process killed, not a command that failed. This repo commits binary art, so the image grows with every accessory. On 1 September .replitignore was given .git (457MB), docs, qa, screenshots and review-sheets, 511MB in all, and the very next publish went straight through. Never use "Fix with Agent" on this: it edits the Repl only, and the fault is not in the code.

Ops

"External database detected" does not block publishing.The banner offers to fix itself by removing DATABASE_URL from Secrets. Do not. That secret is the only thing pointing at the external Postgres, and removing it repoints the live app at an empty Replit database. All the banner actually does is DISABLE the publish-time dev-to-prod migration diff, which matters only when a change carries a migration. Publishes succeeded with it showing on 1 September.

Data

There are two databases and the Shell is not the one users touch.The Repl Shell holds development. Production is a separate Neon endpoint and they are divergent. A count from the Shell is not an answer.

Builds

Ad hoc and preview builds crash 10 out of 10, whatever is in them.Only store builds through TestFlight tell the truth. Roughly fifteen builds of one investigation measured nothing but this artefact.

Builds

Your builds are not reproducible.No ios/ committed, no Podfile.lock, no pinned builder image. Two builds of one commit were never guaranteed to be the same app, which is why a week of bisecting produced nothing.

Release

The 1.0.0 train is closed.Every iOS submission needs expo.version bumped, not just ios.buildNumber. Error 90186 closes TestFlight too, so it blocks internal testing and not just release.

Release

EAS autoIncrement writes the number back into app.json.The build you get is one higher than the number you committed, and the tree comes back dirty. That is documented behaviour, not a mistake to revert mid build.

Release

An interrupted eas submit may already have uploaded.A backgrounded submit was stopped before printing anything, its log held only [killed], and that emptiness was read as "it never ran". It had already uploaded. The retries then failed with a bare "Something went wrong when submitting your app", and the real message was only on the Expo submission page: "Build number 533 for app version 1.0.10 has already been used". That error is PROOF OF SUCCESS. Before resubmitting an interrupted build, assume it landed and check. 1 September.

Push

Android push needs a rebuild before it can deliver anything.The Firebase project bolo-9bf9a exists and app.json points at google-services.json, but that file is compiled into the binary. Build 503 was made at 01:04 UTC and the file landed at 18:40 UTC, so the app on Play has no Firebase in it.

Push

Nothing in the repo calls the push cron.The streak reminder wants an hourly caller and there is no GitHub action and no schedule in .replit. If one exists it was made in the Replit UI, where this page cannot see it. Until that is confirmed, no reminder fires on either platform.

Push

The FCM v1 key belongs in EAS credentials, never in the repo.google-services.json is safe to commit and already is: its Android key is restricted by package name and ships inside the app anyway. The service account key that actually sends is a different file and a real secret. Confirm with eas credentials before assuming Android can send.

Mobile

The native animation driver is dead in release builds.useNativeDriver must be false everywhere. Anything driven per frame from the native side does not tick.

Mobile

expo-image must not be imported anywhere in the mobile app.It crashed five cold starts out of five, twice. A census test guards it. expo-image-picker is a different package and is fine.

Crashes

Read the device crash reports, not Sentry.Sentry silently stopped delivering these once while the phone kept writing them, and that silence was read as success three separate times.

Crashes

Server errors reached Sentry for the first time on 1 September.For the app's whole life the api-server sent nothing, while /friends/feed returned 500 to every learner and no alert fired. Two faults. setupExpressErrorHandler cannot work because esbuild inlines express into the bundle and Sentry patches express as a module; that one is STILL unfixed and needs express external in build.mjs. The one that mattered: pino-http builds req.log with .child(), and the Sentry-forwarding Proxy did not intercept child, so every unhandled route error wrote a perfect log line and reported nothing. A test on the base logger passes either way, which is why it hid for a month.

Analytics

The mobile app reports, but not which store it came from.React Native events carry no OS property and build numbers collide across platforms, so iOS and Android cannot be separated. Register Platform.OS as a super property to fix it. An earlier version of this page claimed mobile sent nothing at all: that was wrong, and it came from reading absent AUTOCAPTURE events as an absent SDK.

Git

The Repl's main sits ahead of GitHub, and that is not divergence.A stack of "Published your App" commits. Run git diff --stat origin/main HEAD before worrying about the log.

Content

Eleven of the twelve reading passages are unverified.Hindi came off the list on 24 August, checked by a speaker against the shipping text. The other eleven are Bengali, Gujarati, Gurmukhi, Tamil, Telugu, Kannada, Malayalam, Odia, Nastaliq, Ol Chiki and Meetei Mayek, and the build names them on every run.

Content

Gujarati is unverified despite having a yes.Bharti approved it, but the stored passage_text beside her answer is the older wording she later complained about, so the verdict does not apply to what ships. That is the whole reason the table stores the text next to the answer: a stale yes is catchable. Never count yeses without comparing the text they were given.

Content

The verification flag is dead code.Marking a passage verified drives one console.warn in buildAksharmala.ts and nothing else. verifiedPassages() is exported and has zero callers, and aksharmala.html rebuilds byte identical. So a verified passage changes nothing a learner can see, and nobody should read the Hindi change as something that shipped.

Content

Ignore anything from "Test Aakesh".Those rows are a walkthrough, not handwriting. isTestContributor drops them by default, along with anything starting "test".
